# FlowHub 基线提交建议

版本：`v0.1.0`  
更新时间：`2026-03-15`

## 1. 用途

本文件用于指导 FlowHub 仓库形成第一个可追踪的发布基线。

当前仓库功能已经基本闭环，但若没有基线提交：

- 后续变更难以审计
- 发布差异难以定位
- 回归范围难以确定

## 2. 建议目标

建议先形成一个“可运行交付基线”，再继续做生产化运营增强。

这个基线建议包含：

- Backend
- Frontend
- Client
- OpenClaw Plugin
- 交付文档

## 3. 不建议混入首个基线的内容

以下内容建议不要和首个基线混在一起：

- `.env` 中的真实密钥
- 本地数据库文件
- 构建产物
- 临时缓存
- 本地联调脚本输出

## 4. 建议的提交分组

### 4.1 基础平台

建议范围：

- `backend/`
- `frontend/`
- `client/`
- `docker-compose.yml`

建议提交说明：

```text
feat: establish flowhub runtime baseline
```

### 4.2 OpenClaw 接入

建议范围：

- `openclaw-plugin/`
- `openclaw-plugin/internal-maintenance/`

建议提交说明：

```text
feat: add openclaw orchestration bridge
```

### 4.3 文档与交付材料

建议范围：

- `README.md`
- `PROJECT_GUIDE.md`
- `DEVELOPER_GUIDE.md`
- `PRODUCT_OVERVIEW.md`
- `docs/delivery/`

建议提交说明：

```text
docs: add delivery and operations documentation
```

### 4.4 参考 Skill 资产

建议范围：

- `find-skills-0.1.0/`
- `self-improving-agent-3.0.1/`
- `skill-vetter-1.0.0/`
- `商业.md`

建议提交说明：

```text
docs: preserve reference skills and commercialization notes
```

## 5. 推荐的首个基线标签

如果准备做正式基线，建议在首个完整提交后打标签：

```text
v0.1.0-baseline
```

适用前提：

- 后端测试通过
- 前端构建通过
- 客户端 typecheck 和 build 通过
- OpenClaw 插件语法通过

## 6. 推荐的 `git add` 顺序

如果你要按“低风险、可回滚、便于审计”的方式形成首个基线，建议按下面顺序暂存：

### 6.1 基础平台

```bash
git add .gitignore .env.example docker-compose.yml hub.json
git add backend frontend client codex-scripts
```

说明：

- 这一步形成可运行平台基线
- 不包含 `.env`、数据库文件和本地缓存

### 6.2 OpenClaw 接入

```bash
git add openclaw-plugin
```

### 6.3 文档与交付资料

```bash
git add README.md PROJECT_GUIDE.md DEVELOPER_GUIDE.md PRODUCT_OVERVIEW.md ClawFlow.md
git add docs/delivery
```

### 6.4 参考 Skill 资产与商业方案

```bash
git add find-skills-0.1.0 self-improving-agent-3.0.1 skill-vetter-1.0.0 商业.md
```

### 6.5 暂存结果复核

```bash
git status --short
```

检查重点：

- 不应出现 `.env`
- 不应出现 `*.db`
- 不应出现 `.next`、`node_modules`、`target`
- 不应出现 `frontend/.next-dev*.log`

## 7. 建议的提交前检查

```bash
git status --short
python3 -m pytest backend/tests -q
cd frontend && npm run lint && npm run build
cd ../client && npm run typecheck && npm run build
cd .. && npm exec -- node --check ./openclaw-plugin/index.js
```

## 8. 当前建议保留为后续提交的事项

这些更适合在基线之后单独继续提交：

- 安装包签名和正式发布流程
- webhook 告警运营模板
- 多租户和生产调度能力
- OpenClaw 线上部署差异

## 9. 建议结论

当前最稳妥的方式不是立即把所有后续优化混成一个大提交，而是：

1. 先建立 `v0.1.0-baseline`
2. 再按“客户端发布治理 / 运维模板 / 生产环境接入”继续细分后续提交
