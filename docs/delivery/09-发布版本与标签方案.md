# 09 发布版本与标签方案

版本：`v0.1.0`  
更新时间：`2026-03-15`

## 1. 文档目的

本文件用于明确：

- 当前推荐发布版本号
- 首次正式发布的 git tag 方案
- 后续补丁和预发布版本的命名规则
- 发布时建议执行的最小 git 命令

## 2. 当前推荐版本

当前仓库已完成一次基线提交：

- 基线提交：`de9be7d`
- 提交信息：`feat: establish FlowHub baseline`

建议将这次首次可交付版本定义为：

- 仓库发布版本：`v0.1.0`

当前仓库内主要端的版本也已经对齐为 `0.1.0`：

- `frontend/package.json`
- `client/package.json`
- `client/src-tauri/tauri.conf.json`

后端当前未单独维护 Python 包版本号，因此以仓库整体版本为准。

## 3. 推荐标签策略

### 3.1 仓库主标签

首次发布建议只打一个仓库级标签：

- `v0.1.0`

这个标签应指向基线提交或通过最终生产验收的同一提交。

### 3.2 预发布标签

如果需要先做灰度或候选版本，建议使用：

- `v0.1.0-rc.1`
- `v0.1.0-rc.2`

适用场景：

- 目标环境联调
- OpenClaw 正式实例验证
- 客户端安装包签名验证
- 外部 AI 生产账号验证

### 3.3 补丁版本

若 `v0.1.0` 之后只做兼容性修复或配置修复，建议递增 patch：

- `v0.1.1`
- `v0.1.2`

### 3.4 次版本

若后续新增对外功能或交付范围明显扩大，建议递增 minor：

- `v0.2.0`

适用示例：

- 新增收费版或精品工作流能力
- 新增多租户权限体系
- 新增客户端正式安装和发布通道

## 4. 推荐分支命名

建议后续采用以下命名：

- 发布分支：`release/v0.1.0`
- 补丁分支：`hotfix/v0.1.1`
- 常规功能分支：`feat/<topic>`
- 修复分支：`fix/<topic>`

如果当前仍处于单人迭代阶段，也可以先不强制建立 release 分支，直接在主分支完成验收后打标签。

## 5. 首次正式发布建议

### 5.1 当前建议口径

如果本地和目标环境的部署验收结果一致，建议采用：

- 正式版本：`v0.1.0`
- 发布对象：基线提交 `de9be7d`

### 5.2 暂不建议立即打 tag 的情况

如果以下任一项尚未完成，建议先保持“候选版本”状态：

- OpenClaw 目标环境未完成真实接入
- 生产 AI Key、配额和告警未验证
- 客户端安装包签名与分发策略未落地
- 首轮生产环境参数未确认

## 6. 推荐 git 命令

### 6.1 创建候选标签

```bash
git tag -a v0.1.0-rc.1 de9be7d -m "FlowHub release candidate v0.1.0-rc.1"
```

### 6.2 创建正式标签

```bash
git tag -a v0.1.0 de9be7d -m "FlowHub release v0.1.0"
```

### 6.3 推送标签

```bash
git push origin v0.1.0
```

如果先走候选版本，再转正式版本：

```bash
git push origin v0.1.0-rc.1
git push origin v0.1.0
```

## 7. 版本变更时需要同步的位置

若后续升级版本号，至少同步这些文件：

- `frontend/package.json`
- `client/package.json`
- `client/src-tauri/tauri.conf.json`
- `README.md`
- `docs/delivery/README.md`
- 本目录中涉及版本展示的交付文档

## 8. 当前建议结论

当前最稳妥的发布策略是：

1. 保持基线提交 `de9be7d`
2. 先完成目标环境部署和生产参数确认
3. 如需联调，先打 `v0.1.0-rc.1`
4. 验收通过后，再打正式标签 `v0.1.0`
